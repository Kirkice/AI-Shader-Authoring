# Shader Review 主编排接入协议

## 加载与适用边界

执行本流程时，完整读取 [Review 原始规范](shader-review/review.md)，并按其要求读取 rules/ 中的全部具体规则及命名参考表。所有脚本路径均相对于本文件所在目录解析，不依赖当前工作目录。

本协议只增加编排与用户确认，不修改原 Review 规则、工具、白名单或命名数据。默认禁止使用 `--legacy` 绕过存量保护，不自动刷新白名单或规范表。

- 代码 Review 仅适用于 `Assets/Shaders/ShaderTheseus/**` 与 `Assets/Shaders/ShaderLibrary/**`，以工具 `_scope.sh` 为准。
- 白名单完整路径命中的存量文件不检查、不报告代码问题、不修改；仅记录跳过原因。原主流程若计划修改此类文件，必须暂停并选择新建非白名单派生文件等方案，不能以用户批准修复为由绕过保护。
- 范围外文件不检查、不报告代码问题、不给 Review 修改建议；标记 `skipped_out_of_scope`，不等于 Review 通过，也不影响原主流程自身的编译、对齐和视觉检查。
- P001 独立于代码扩展名和白名单：ShaderLibrary 内任何文件的新增、修改、删除、移动、重命名均需事前确认。用户批准修复不替代 P001 的群内确认。

## 用途分类与 Review 范围独立

两条实现路线（reference/pbr）均执行本 Review 闭环。每轮记录 domain、route、confirmedScopeVersion、selectedBaseline 与 reviewedRevisions。知识库用户确认的特效/场景/角色/共享库目录只用于检索与实现，不自动修改 Review 的 `_scope.sh`、白名单或 P001 路径范围。

角色样本归纳的命名表不应被推断为已验证的场景/特效通用命名事实。仍按原规则检查其适用范围并报告真实命中；若与同类型参考、GUI 或材质兼容契约冲突，必须列出双方依据，暂停相关修改并请求方案确认，不静默重命名、不自动改规则，不以“新类型”自动豁免。范围外继续标记 skipped，不伪造 Review 通过。

## A. 写入前预检

在 Code Plan 形成后、Step 6.5 用户确认与首次资产写入之前执行：

1. 记录计划目标、工程根、相对 Assets 路径、当前 revision、范围与白名单状态；不存在的新文件按计划路径判断。
2. 对范围内新文件，先查命名规范，检查计划中的功能开关、切线约定、uniform 与 keyword。尚无源文件时不得伪称已执行代码扫描。
3. 检查 ShaderLibrary 计划改动与实际 Git 改动。重命名、移动必须同时检查旧路径和新路径；可以使用 `git diff --name-status --no-renames`、`git diff --cached --name-status --no-renames` 及 `git ls-files --others --exclude-standard`，解析路径后按目录前缀匹配。无 Git 信息时记录不可用，依据计划及操作记录核实，不能断言不涉及审批。
4. P001 未确认则停止写入。按原规则提供消息草稿，不擅自发送。
5. Review 规则与参考基线完整继承、GUI 属性契约或材质迁移要求冲突时，列出双方依据及影响，进入 `BLOCKED`；不得静默改名、删属性、继承已知错误，或通过换路径规避审查。需要改变原确认范围的方案必须重走 Step 6.5。

## B. 生成后 Review

Step 7 写入并通过编译/Console 门禁，且完成适用的 Step 7.5 GUI 后处理及复编译后，在 Step 8 验收之前执行：

```bash
bash <本文件目录>/shader-review/tools/scan.sh <本轮目标文件...>
bash <本文件目录>/shader-review/tools/naming-lint.sh <本轮目标文件...>
```

仅对适用且非白名单文件执行代码检查。每轮记录命令、输出、退出码、审查文件 revision、范围/白名单跳过统计、P001 状态。脚本失败、目标不存在、零候选或无法运行必须分别报告，不能当作全部通过。`scan.sh` 的退出码不代表无问题，必须读取输出；命名检查退出码 1 表示发现错误，不能丢弃报告。

扫描只筛候选，必须阅读上下文、Include 和相关 Pass，按规则误报提示人工核实。未核实项标记待确认，不得自动修复。新文件从存量参考复制而来的已知问题仍应检查，但不得回头修改白名单参考文件。

## C. 向用户提交修改项并等待

每轮 Review 完成后必须输出：

```text
## Shader Review 第 {round} 轮
- 审查版本：{文件与 revision}
- 范围/白名单跳过：{数量、原因}
- 扫描与人工复核状态：{已完成/未完成及原因}
- P001：{不涉及/待确认/已确认及依据}

| 编号 | 文件:行 | 规则/级别 | 已确认的问题 | 建议修改 | 影响/风险 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| REV-001 | ... | ... | ... | ... | ... | 待用户确认 |

- 待核实项/规则冲突：...
- 本轮未自动修改任何 Review 问题。
请确认要修复的编号；修复后会再次 Review。若无需继续修改，请明确同意进入验收。
```

没有修改项也必须报告“无已确认修改项”，等待用户同意进入验收；不得自己代替用户确认。用户仅说“修复”只授权修复本轮清单中明确的问题，不代表提前同意验收。部分授权只修复对应编号，其余保留。拒绝或延期项须记录理由、风险及是否阻断。

## D. 受控修复与再次 Review

1. 用户授权后，将批准的编号、修复范围、确认版本写入 Code Plan；执行前核验 revision，变化则先重新 Review 并重新确认，不把旧授权套用到新代码。
2. 原有资产白名单、P001、Step 6.5 功能属性确认和参考契约继续生效。新增资产、功能/参数变化必须先更新计划并重新确认。
3. 只修复批准项。修复产生写入后，重走 Step 7 编译、job 轮询、Console 检查；需要时重走 GUI 子流程及复编译，不允许绕过原有最多三轮编译错误修复限制。
4. 编译通过后重新扫描并人工复核本轮全部适用目标，不仅检查已修复行。输出新一轮清单，标注已修复、仍存在、新增、延期和待核实项；返回 C 等待确认。
5. 用户确认修复/重新 Review 的交互循环不设置自动通过轮数；用户可暂停或终止。工具不可用、无法编译或授权冲突进入 `BLOCKED`，不得无限自动重试。

## E. 用户同意验收与失效规则

只有用户针对最新 Review revision 明确同意进入验收，且无未解决的阻断项，才记录 `user_review_accepted` 并进入 Step 8。非阻断建议可由用户明确接受风险并延期；编译错误、P001 未确认、白名单保护、必需证据缺失及原主流程硬性门禁不得以接受风险豁免。

Review 全部跳过时记录 `skipped`，解释适用边界，并同样等待用户同意进入原主流程验收，不伪造 Review 通过。

用户同意进入验收不等于最终 PASS。Step 8 全部既有技术门禁仍必须执行。验收后展示结果，等待用户明确接受最终验收；拒绝则整理修改项并回到计划/授权、修复与 Review 循环。技术条件未满足时，即使用户说满意也不能标记 PASS。

任何验收修复、GUI 元数据修改或其他对已审查文件的写入都会使对应 Review 与用户接受记录失效；重新编译、Review，并让用户重新确认。用户追加功能或调整属性时同时重走 Step 6.5。

## 结果记录

每轮至少保存：`round`、`reviewedRevisions`、`scopeStatus`、`skippedFiles`、`scanDiagnostics`、`manuallyConfirmedFindings`、`unresolvedItems`、`p001Status`、`approvedFixIds`、`deferredItems`、`userConfirmation`、`compileDiagnostics`、`nextAction`。

最终报告补充 Review 各轮摘要、已修复/延期项、跳过项、P001 依据、用户同意进入验收的版本，以及最终验收的用户接受状态。未完成任何一步必须明确标记，不得以空清单替代执行证据。
