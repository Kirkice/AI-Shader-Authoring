# AI Shader Authoring 安全与可靠性达成路径

## 1. 目标与实施边界

将现有“Skill 约定 + 结构化 MCP 工具”升级为执行层可验证、失败可恢复的材质生产流程。

本文件仅为实施计划，不代表已完成安全审计、测试或代码修复。不修改现有业务资产，不触发知识库构建或 Shader 生成。

优先顺序：可信执行入口 → 授权与写入 → 工程事实与任务恢复 → 编译/视觉证据 → 性能与维护。

### 现有协议基线

- [安全执行协议](shader-skill-mcp-execution-protocol.md)：复用既有授权范围、阶段授权和恢复规则，不另建冲突的权限模型。
- [数据交接契约](shader-authoring-data-contract.md)：复用不可变对象、版本与证据关联原则。
- [MCP Bridge 说明](../Packages/com.ai.shader-authoring/Documentation~/MCP_BRIDGE.md)：保留已有 Editor 精确绑定、请求关联和取消行为。

### 对前期风险判断的校准

1. 知识库状态查询目前将持久化新鲜标志用于指纹匹配结论，这是已读代码中可确认的缺口，不能据此断言当前工程确实新鲜。
2. 动态 C# 是完全信任入口，不等于已经发生漏洞利用；它的编译能力还受 Unity 版本限制，但不能把“不一定能编译”作为安全隔离。
3. Bridge 文档已经说明多 Editor 绑定和响应匹配，不能将其视为完全未实现。认证、防重放、断线隔离需检查两端实际实现后确定增量。
4. 结构化工具分发和动态命令入口不同，不能把结构化分发本身描述为任意代码执行。
5. Job 恢复、视觉会话清理、原子发布及超时情况尚需针对实现和测试核验；先标记待核验，不直接宣布缺失。
6. 本包现有测试目录主要为场景和材质；全仓自动化覆盖率必须在阶段 0 清点，不能仅由目录名推断。

## 2. 里程碑与依赖

| 阶段 | 目标 | 依赖 | 估算工程日 | 退出条件 |
|---|---|---|---|---|
| M0 | 核验风险、建立回归基线 | 无 | 1–2 | 问题均有代码证据或复现，正常流程可重复 |
| M1 | 收紧连接与高权限入口 | M0 | 3–5 | 未认证调用不能执行，默认禁止动态命令 |
| M2 | 授权落地与事务写入 | M1 | 4–7 | 伪造计划、越界写入、冲突和重放被拒绝 |
| M3 | 知识库可信度与任务恢复 | M2 | 4–7 | 过期知识不放行，重启不会伪报成功 |
| M4 | 编译及视觉证据可信度 | M3 | 5–8 | 无效目标、错误版本和失败编译不能通过验收 |
| M5 | 性能报告、兼容性与发布 | M4 | 3–5 | 缺失性能输入不阻断视觉，回归矩阵通过 |

估算为单名熟悉 Unity/Node 的工程师的净工程日，共 20–34 日；不含等待 Unity 平台模块、真机或人工视觉审核。M0 后根据证据重新估算。大范围 Shader 语义分析不纳入首版承诺。

建议分两次交付：M2 为“受控内测安全基线”，M5 为“团队可维护发布基线”。M2 不代表渲染正确性已获得完整保障。

## 3. M0：核验与测试基线

### 工作

- 清点 Unity、Node 两端工具注册、请求校验、动态命令调用链、写入路径、外部进程、Job 和场景副作用。
- 对每个问题记录：已确认/待核验/已有防护、触发条件、代码位置、最小复现、影响、对应测试。
- 检查现有计划中的失效链接和缺失契约，补齐前先确认真正的工具定义来源。
- 建立三个测试层：Node 协议单测、Unity EditMode 测试、完整 MCP 集成测试。
- 固化当前不透明 PBR 正常流程；单独记录裁剪、透明、GUI 与性能链路，不以一张截图代替全链路回归。

### 落点

- [Unity 连接层](../Packages/com.ai.shader-authoring/Editor/Mcp/UnityMcpConnection.cs)

- [测试目录](../Packages/com.ai.shader-authoring/Tests)

### 验收

- 每个 P0/P1 问题均有可重复测试或明确的尚未验证说明。
- 相同输入的正常流程可连续执行两次，并产生可关联的编译与材质证据。
- 自动化命令、Unity 版本、平台支持情况和测试结果存档；未运行项不标记通过。

## 4. M1：可信连接与诊断入口隔离

### 工作

1. 默认同时关闭 Node 工具暴露、Unity 接收分支和 Dashboard 中的动态命令执行；不能仅隐藏 UI。
2. 开发诊断模式必须由本地人工显式启用；针对具体命令内容摘要批准，禁止远程自批。界面明确提示：任意 C# 与 Editor 同权限，超时不能可靠终止正在主线程执行的代码。
3. 保留现有 Editor 精确绑定，增加项目级配对凭据、双向握手与连接代次校验。凭据不提交仓库、不写日志、不作为普通 Agent 工具返回值。
4. 默认只允许回环地址。远程模式必须显式开启并使用经验证的 TLS 或受保护隧道；认证不能替代传输保护。
5. 请求绑定会话、项目、Editor 和连接代次；增加时效、重放缓存、消息体大小上限和速率限制。
6. 连接中断后，不自动重放写入、恢复和场景修改操作。

### 验收

- 未配对、凭据错误、过期、重复及旧连接请求均被拒绝且无副作用。
- 两个 Unity 项目并行时，请求不能跨项目执行。
- 默认模式通过 Node、直接协议消息和 Dashboard 均不能调用动态命令。
- 凭据轮换后旧会话失效；日志不含凭据。

### 边界

认证防止未授权对端，不防御已控制同一操作系统用户或 Unity 进程的攻击者。不承诺进程内沙箱。普通诊断优先补充结构化只读工具，避免关闭动态入口后失去必要能力。

## 5. M2：真实授权与事务写入

### 工作

1. 将现有阶段授权协议实现为 Unity 侧不可变计划注册表。Agent 只能提案；本地可信 UI 或独立可信审批通道才能批准。
2. 授权绑定项目、会话、运行、计划内容摘要、工具能力、路径、基线版本、到期时间与写入预算。
3. 请求提交授权引用；执行端查登记记录，不信任请求自行提交的允许文件集合。计划变化必须重新批准。
4. 明确同计划多轮修复的版本推进规则：成功提交后原子登记新版本；人工修改造成版本变化必须回到冲突处理，不能静默更新基线。
5. 统一资产与工件路径校验：规范化绝对路径、边界分隔符比较、Windows 大小写规则、文件类型允许列表、符号链接/目录联接限制。运行标识不得直接成为未校验路径片段。
6. 临时文件先写入非导入目录并校验，保存备份和事务记录后再替换目标；多文件任务明确提交边界。不得把逐文件原子替换称为跨文件原子事务。
7. 恢复操作遵守现有协议：需单独授权，校验当前版本且不覆盖人工新增修改。进程中断只进行已授权事务的安全恢复，不自动扩大范围。
8. 写入后导入失败仍保留事务和失败版本，返回明确状态而非“未执行”。

### 验收

- 自行构造计划 ID、授权 ID、额外文件或扩大操作能力都不能写入。
- 授权撤销、过期、预算耗尽后立即生效；重放不重复扣减预算或写入。
- 路径穿越、目录联接越界和非允许文件类型测试全部被拒绝。
- 人工在检查后修改资产时不能被静默覆盖；需定义受控锁和提交前复核策略，并测试竞争情况。
- 写入各阶段注入异常后，目标保留旧完整版本或新完整版本，不出现半文件；部分多文件提交可识别、可恢复。

## 6. M3：知识库与 Job 可靠性

### 知识库工作

- 状态读取重新核对 Schema、Manifest、环境与源依赖版本，区分新鲜、过期、缺失、未知和损坏。
- 快速检查结合增量失效标记；生成前核对实际使用的 Shader/Include。不能只依赖时间戳、文件监控或持久化的新鲜标志。
- 记录依赖闭包：Shader 内容未变而 Include 变化时同样失效。
- 知识库新版本完整生成并验证后才原子切换当前指针；失败不覆盖最后成功版本。
- 检索先按管线、版本、能力状态和来源有效性过滤，再进行关键词排序。无适用结果明确返回覆盖缺失。
- 向量检索为后续可选优化，不是可信度修复前置条件。

### Job 工作

- 持久化输入摘要、请求归属、目标版本、授权引用、状态与输出摘要。
- 幂等键与输入摘要绑定：同键同输入复用；同键不同输入报冲突。
- Domain Reload 或重启后未完成任务标记中断/丢失，核对工件后才允许恢复；非幂等任务不自动重放。
- Unity API 保持主线程执行；纯文件分析可后台运行。耗时同步工作拆片，设置队列上限、并发限制和保留策略。
- 区分请求取消和实际终止；不能虚报已取消。外部分析器使用可终止的进程边界。

### 验收

- 修改包配置、Renderer 配置、参考 Shader 或依赖 Include 后，相关知识不可继续报告已核验新鲜。
- Manifest 缺失、损坏或 Schema 不兼容不能放行。
- 重启后任务可追踪，未完成任务不会变成成功；重复请求不重复产生副作用。
- 长任务执行期间 Dashboard 保持可操作；在 M0 固定规模夹具上记录最大主线程停顿及 P95，目标为调度分片不超过 50 ms，Unity 不可分割原生调用单独报告，不虚报满足预算。

## 7. M4：编译、结构对齐和视觉证据

### 结构对齐：分层实现，不承诺完整语义证明

- 第一层：词法处理去除注释干扰、处理块边界，提取属性类型/默认值、关键字、Pass、标签、Include、入口及渲染状态。
- 第二层：参考与目标差异生成机器报告，未授权差异阻止进入最终通过；用户批准的偏差记录与计划摘要绑定。
- 第三层：纹理通道、宏分支、工作流接线用项目定向规则与测试材质验证。静态分析无法证明的内容明确标记未知，交人工审核，不以属性存在代替实际采样。
- GUI 维护采用限定注释区域与 Editor 声明的专用修改路径；验证渲染代码及属性语义未变化。

### 编译证据

- 绑定编译请求、Shader/Include 依赖摘要、材质版本、Unity/管线版本、目标平台和图形 API。
- 等待导入和编译稳定后采集权威错误状态；日志时间游标只去除旧噪声，不取代编译状态。
- 不清空用户 Console；保留本轮日志窗口，并单独报告无法归属到目标资产的错误。
- 门禁状态由执行层保存，截图工具核对同一版本的有效编译证据。

### 视觉证据

- 固定场景是夹具来源，不是允许保存修改的业务场景。测试前保存用户场景布局、活动场景、选择和脏状态；隔离会话结束或异常时恢复。
- 保持本轮真实材质资产的绑定与回读，记录实例、槽位、贴图、参数和版本；参数扰动采用受控测试资产写入或显式测试覆盖，不能伪装为最终交付材质证据。
- 固定时间、光照、曝光、相机和背景；对时间驱动效果使用指定采样时刻。
- 检查目标包围盒投影、占屏比例，增加目标 mask 与区域像素差异，整图 hash 只作为辅助。
- 同输入重复捕获建立噪声基线，再用显著参数变化验证响应；阈值按测试夹具预先登记。
- 人工视觉审核保留，自动化只判定证据有效性，不宣称证明艺术目标全部正确。

### 验收

- 编译失败、证据过期、材质/依赖版本不符时不能生成通过结论。
- 删除参考 Pass 或关键工作流且无批准偏差时失败。
- 仅 GUI 标记修改测试证明属性和渲染语义未改变。
- 目标在画面外、被遮挡、绑定错误或只背景变化时，负例不能通过。
- 正常不透明、裁剪、透明和时间驱动用例分别验收。
- 成功、失败、取消三种结束路径均恢复用户场景状态；磁盘夹具不被意外改写。

## 8. M5：性能、兼容与发布

### 工作

- 性能报告独立表达输入可用性、覆盖范围、分析结论和预算评级；不强迫它们成为单一互斥状态。
- 分别注明静态估算、Unity 平台编译、离线 GPU 分析和真机 Profiling 的证据等级。
- 报告关联源及依赖版本、变体关键字、Stage、GPU、编译器版本与参数。旧报告不显示为当前结果。
- 固化实际支持的 Unity/URP 版本矩阵；内部编译导出 API 不兼容时给出明确原因并继续静态/视觉流程。
- 工具定义、Dashboard 描述和协议文档建立一致性测试；逐步从单一契约源生成，避免三处手工漂移。
- 拆分工具路由、授权、存储、知识库、Job、编译与验证模块；在测试覆盖后拆分，不先进行大规模重写。

### 验收

- 无 Mali、无 Android 模块、零导出变体及分析器失败时均有准确状态，并继续视觉验收。
- 成功分析报告可追溯到精确输入；不把桌面截图或离线估算标记为真机性能通过。
- 声明支持的版本组合全部通过对应测试，不支持的组合明确降级或拒绝。
- 文档和工具表一致；所有 P0/P1 回归及正常端到端流程通过后才发布。

## 9. 合并与验收回路

每个里程碑独立分支/PR，避免安全改造和功能扩展混在一次提交中。

1. Architect 固化本阶段范围、测试夹具和通过/不通过标准。
2. Code 仅实现本阶段，执行相关回归。
3. 执行报告包含完成项、未完成项、实际修改文件、偏离计划及逐条测试证据。
4. Architect 按原标准验收；失败项形成定向修复任务，最多三轮，仍失败则阻断该里程碑。
5. 不因文档完整或演示成功而替代测试证据；未运行的 Unity 集成测试必须标记未验证。

## 10. 迁移、回滚与近期行动

### 迁移

- 协议版本协商；旧客户端在升级后最多保留只读能力，不绕过新授权。
- 旧知识库进入待验证状态，不直接删除；验证通过后复用，否则请求用户批准重建。
- 旧 Job/性能/截图证据保留可读但标注历史，不自动用于新版本通过判定。

### 回滚

- 发布前记录代码版本、协议版本及工件 Schema。
- 回滚应用代码不回滚安全策略到匿名写入；不能安全降级时停止写入、保留只读诊断。
- 不自动删除用户资产或旧证据。恢复资产必须走单独授权与版本冲突检查。

### 第一批执行清单

- [ ] 完成 M0 风险证据清单与基线回归。
- [ ] 完成 M1 默认禁用动态执行及配对认证。
- [ ] 完成 M2 授权登记、统一路径校验和可恢复写入。
- [ ] 通过受控内测安全基线验收后，再进入知识库与视觉可信度改造。

最终目标不是增加更多 Skill 条款，而是让关键条款在执行端自动生效：未授权不能写、知识过期不能放行、错误版本不能复用证据、任务中断不能伪报成功、性能缺失不能阻断视觉验收。
